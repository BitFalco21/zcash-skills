**Before preparing a replacement**

Reconcile the original txid and saved bytes/expiry, including a wallet journal left behind before server recording. In `submit_saved_prepared`, a known mempool transaction remains pending; canonical inclusion confirms the original. If absent, `original_after_absence` reads chain height and **looks up the original again**. Replacement requires continued absence, **nonzero expiry**, and tip height **≥ expiry height**. Inclusion at the expiry boundary still wins. Zero expiry, RPC failure, malformed evidence, or noncanonical inclusion does not authorize replacement.

Only then does `submit_address_prepared` call `reset_address_for_retry`; `execute_address_payment` passes the old txid as replacement authorization under the same operation. `RealWallet::prepare_in` requires the corresponding journal. A lost broadcast response triggers another transaction lookup; uncertainty remains pending. These gates are in [payments/submission.rs:238](/private/tmp/zcash-skills-eval-followup-20261016/faucet-lost-response/without-skill/crates/ths-server/src/payments/submission.rs:238).

**Confirmation** requires matching transaction identity, positive confirmations, a nonempty block hash, and that hash matching the canonical hash at its height. `confirm_address_after_mining_with_attempt` checks inclusion, mines/synchronizes if pending, then checks again. `Store::confirm_address` updates only the matching operation/txid. See [payments/confirmation.rs:20](/private/tmp/zcash-skills-eval-followup-20261016/faucet-lost-response/without-skill/crates/ths-server/src/payments/confirmation.rs:20).
