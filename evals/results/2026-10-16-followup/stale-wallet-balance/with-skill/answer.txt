The first check is artifact identity: launching a container after editing server source does **not** establish that it contains those edits. Health 200 also does **not** establish a current wallet snapshot. Neither proposed workaround addresses those boundaries.

**Observed in source**

- [Dockerfile](./Dockerfile) copies the compiled server and built dashboard into the app image. `crates/ths-cli/src/runtime/images.rs::{app_image,build_project_images}` selects a version-tagged image; startup requires existing images rather than rebuilding source.
- `crates/ths-server/src/api/status.rs::health` requires startup completion, a responding node, and **any previous successful sync**. It does not require the current sync state to be `ready`.
- `state.rs::AppState::accounts` reads the published snapshot. `sync.rs::refresh_wallet_snapshot_until` applies SDK balances and validates checkpoints before replacing it. Sync failure preserves earlier balances and records an error.
- `bootstrap.rs::init` configures mining to treasury account **6**. `/accounts` exposes accounts **1–5**, so mining alone need not increase the displayed user total.

**Diagnostic procedure — proposed, not executed**

1. **Establish the running artifact and instance.** Record the source revision/local diff, instance name, endpoint mapping, app container’s immutable image ID, and build provenance. Compare the container’s image ID with the intended rebuilt image; a matching tag alone is insufficient.

   Owners: `Dockerfile`, `crates/ths-cli/src/runtime/{images,startup}.rs`. `web/vite.config.ts` confirms that `THS_DEV_API` only proxies frontend requests to an existing server.

   After preserving failure evidence and wallet data, a later controlled reproduction should use the documented `cargo run -p thus-spoke-zakura -- build --dev` followed by a **new named instance**. Rebuilding does not replace an existing container.

2. **Separate chain progress from snapshot publication.** Against that same instance, capture timestamped raw responses from `/api/v1/status`, `/api/v1/accounts`, and `/api/v1/mining/jobs`.

   Compare:

   - `node.blocks` and `node.bestblockhash`;
   - `lightwalletd_height`, `wallet_scanned_height`, `settled`, and `settlement_blocker`;
   - `wallet_sync.state`, `error`, `last_success_at`, and observed/scanned **heights and hashes**;
   - mining job state, acknowledged count, error, and `progress_uncertain`.

   `api/status.rs::settlement_status` distinguishes unavailable dependencies, wallet errors, height/hash mismatches, and a wallet behind the tip. Equal heights alone are insufficient. Read raw JSON: `web/src/lib/api/schemas.ts::{walletSyncSchema,statusSchema}` currently omits the wallet hashes and settlement fields.

   If HTTP accounts remain stale, trace `rpc.rs` → `reconcile.rs::{sync_wallet,find_rewind,within_deadline}` → `wallet.rs::apply_balances` → `sync.rs::{synchronize_wallet_until,refresh_wallet_snapshot_until,scan_is_publishable}`. Correlate app/lightwalletd logs with the failed phase. The two-second background interval is a retry cadence, not a freshness guarantee.

   `mining.rs::MiningCoordinator::run` can report all blocks generated but fail subsequent synchronization. Preserve that distinction before repeating mining.

3. **Investigate browser caching only after HTTP accounts are current.** Trace:

   `web/src/lib/api/endpoints.ts::api.accounts` → `client.ts::request` → `schemas.ts::accountSchema` → `hooks/queries.ts::useAccounts` / `queryKeys.accounts` (`['accounts']`) → `features/wallet/WalletPage.tsx`.

   Compare the network response, Zod validation errors, cached account values/query update time, and rendered total. Account amounts become `bigint`; `WalletPage` derives its total directly from query data.

   In `hooks/useServerEvents.ts::TOPICS`, **`wallet` invalidates accounts; `chain` and `sync` do not**. Successful snapshot publication emits `wallet` only when account values change. Mining acceptance invalidates the mining query, so later wallet refresh matters.

   Check `/api/v1/events` delivery and the resulting accounts refetch. `api/events.rs` emits `resync` for subscriber lag, but provides no event IDs/replay across disconnection. `app/providers.tsx` disables focus refetch; its five-second `staleTime` does not schedule polling.
