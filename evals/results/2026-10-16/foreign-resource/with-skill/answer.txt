Reject the proposal. The unlabeled volume is an ownership conflict; its `ths-alpha` name does not authorize deletion. Retrying from Drop would bypass an intentional startup safety boundary.

**Observed production behavior**

- `main.rs` → `lib.rs::run_from` → `args.rs::Cli` → `commands.rs::run` resolves `--name alpha` and dispatches to `Runtime::start`.
- In `crates/ths-cli/src/runtime/startup.rs`, `Runtime::start` calls `own_start` **before Docker/image preflight**. `StartOwnership` holds the startup lock, lifecycle lock, and published session. Production then enters `start_owned`; `start_with` and `start_with_policy` are test adapters.
- `start_owned` creates `CleanupOnDrop` as `Inactive`, then calls `DockerHost::delete` → `cleanup.rs::Runtime::cleanup_core(partial=false)`. It arms the guard only after `CleanupReport::verified()`. Either an initial error or an unverified report returns without allocation or Drop deletion.
- `resources.rs::{owned_resource, inspected_resource_identity}` require an exact, unambiguous name and `com.zakura.ths.instance=alpha`. Missing and foreign labels both produce “refusing to reuse or delete it.” `ensure_network_with`, `ensure_volume_with`, and `create_container` use that ownership boundary for reuse.
- `cleanup_core` preflights the expected containers (`app`, `lightwalletd`, `zakura`, `init`), volumes (`chain`, `wallet`, `lightwalletd`, `config`), and network. An ordinary ownership conflict in initial cleanup prevents **all queued removals**, preserving metadata. It does not delete arbitrary prefix matches.
- After verified initial cleanup, `DockerHost::allocate` allocates network, volumes, init, Zakura, lightwalletd, then app, recording mutations and identities in `recovery.rs::RecoveryJournal`. Allocation/readiness failures and interruption reach explicit `delete_partial`; the guard becomes `Explicit` first, preventing a second Drop attempt. Startup and cleanup errors are both reported. Browser-open failure keeps the environment running.
- Separately, `cleanup.rs::{stop, reset}` use `verified_cleanup` → `instance.rs::verified_cleanup_with`, which coordinates with the owning launcher and refuses a superseding owner/session before invoking cleanup.

**Safe cleanup and replacement behavior**

`cleanup_core(partial=true)` may remove verified owned allocations while preserving conflicting resources and reporting failure. Unresolved allocations retain dependencies and recovery evidence; metadata is removed only after verified completion and finished helpers.

Recorded container/network IDs take precedence over names (`recovery.rs::identity_matches`). Cleanup must not adopt a replacement even with the same ownership label. Failed inspection alone does not prove absence: `cleanup.rs::prove_recorded_absence` requires a successful identity listing.

There is a limitation: Docker volumes are identified by **name** (`resources.rs::inspected_resource_identity`). The source protects a foreign/unlabeled replacement, but cannot distinguish successive volumes with the same name and matching label.
