Reject the proposal. A matching name does not establish THS ownership, and retrying initial cleanup from Drop would bypass a deliberate safety boundary.

**Observed source behavior**

- Production dispatch is `main` → `run_from` → `commands::run` → `Runtime::start`. In [startup.rs](/private/tmp/zcash-skills-eval-20261016/foreign-resource/without-skill/crates/ths-cli/src/runtime/startup.rs:4), `start` acquires `StartOwnership` through `own_start` before Docker preflight, then calls `start_owned` with `DockerHost`. The launcher owns orchestration; `DockerHost` supplies allocation and cleanup operations.
- [resources.rs: `owned_resource`, `inspected_resource_identity`](/private/tmp/zcash-skills-eval-20261016/foreign-resource/without-skill/crates/ths-cli/src/runtime/resources.rs:24) require an exact resource-name match and `com.zakura.ths.instance=alpha`. Missing or different labels produce “refusing to reuse or delete it.” Prefix deletion could destroy foreign resources and resources of another instance such as `alpha-extra`.
- [cleanup.rs: `Runtime::cleanup_core`](/private/tmp/zcash-skills-eval-20261016/foreign-resource/without-skill/crates/ths-cli/src/runtime/cleanup.rs:71) checks a fixed inventory: four containers, four volumes, and the instance network. Initial cleanup uses `partial=false`; an ownership collision prevents the removal phase, including removal of already-inspected owned resources. Existing metadata remains.
- [startup.rs: `start_owned`, `CleanupOnDrop::drop`](/private/tmp/zcash-skills-eval-20261016/foreign-resource/without-skill/crates/ths-cli/src/runtime/startup.rs:620) deliberately start the guard as `Inactive`. Only verified initial cleanup arms it. An initial error or unverified report therefore returns without allocation or a Drop retry.
- Once allocation begins, failures and interruption receive explicit `delete_partial` cleanup. The guard becomes `Explicit` before that attempt, so its failure is not retried by Drop; startup and cleanup errors are combined. `DockerHost::delete_partial` uses `partial=true`, allowing independently verified owned resources to be removed while preserving foreign collisions.
- Recovery records identities and mutation dependencies. [cleanup.rs: `retained_mutation_resources`, `reconcile_absent_container`](/private/tmp/zcash-skills-eval-20261016/foreign-resource/without-skill/crates/ths-cli/src/runtime/cleanup.rs:576) retain dependencies while allocation remains unresolved. Cleanup verifies absence and finishes helpers before deleting metadata or reporting completion.

Same-name replacements must not be adopted. Containers and networks have recorded IDs; cleanup inspects and removes the original ID. Inspection failure alone does not prove absence: `prove_recorded_absence` requires a successful identity listing. A replacement container also prevents releasing unresolved allocation dependencies. Volumes have only name-based identity here, so label verification protects against foreign replacements; this checkout cannot distinguish two successive same-name volumes carrying the same ownership label.

External `stop`/`reset` use [instance.rs: `verified_cleanup_with`](/private/tmp/zcash-skills-eval-20261016/foreign-resource/without-skill/crates/ths-cli/src/runtime/instance.rs:372): request shutdown from the owning session, wait for ownership, reject a superseding launcher, then verify leftovers. They do not justify unconditional Drop retries.

The safe outcome for this collision is failure with the foreign volume untouched. Resolve that resource separately through its owner, or choose a noncolliding instance name; do not automatically delete or relabel it.
