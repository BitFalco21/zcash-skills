The following diagnostic procedure is proposed, not executed:

1. **Establish the instance and running artifact first.** Record the named instance’s endpoints, browser origin, container identity, immutable image ID/digest, and build provenance. Compare those with the intended source revision; a version tag or container launch timestamp alone is insufficient. Owners: `crates/ths-cli/src/runtime/{images,startup,resources}.rs`, especially `app_image` and app-container creation. For Vite, also verify `web/vite.config.ts`’s `THS_DEV_API` target. A later comparison should use an image built from the intended revision in a separate disposable instance.

2. **Capture raw server evidence together.** Read `/api/v1/health`, `/api/v1/status`, `/api/v1/accounts`, and `/api/v1/mining/jobs` from that same instance; repeat while noting timestamps and chain movement. Record:
   - `node.blocks` and `node.bestblockhash`;
   - `wallet_sync.state`, `error`, `last_success_at`, observed and fully scanned **heights and hashes**;
   - `lightwalletd_height`, `settled`, and `settlement_blocker`;
   - mining job state, acknowledged count, error, and `progress_uncertain`.

   `api/status.rs::settlement_status` distinguishes unavailable dependencies, wallet error/syncing, height mismatch, chain mismatch, and wallet lag. Equal heights can still represent different chains. These are separate reads, so repeat comparisons if the tip moves. Use raw JSON: `web/src/lib/api/schemas.ts` currently omits hashes and settlement fields from its parsed status model.

3. **Locate a stale server snapshot before investigating browser state.** In [sync.rs](/private/tmp/zcash-skills-eval-20261016/stale-wallet-balance/without-skill/crates/ths-server/src/sync.rs), `wallet_sync_loop` retries about every two seconds. Reconciliation waits for indexing, scans, validates canonical checkpoints, then publishes balances. Failure preserves the last good accounts and success timestamp while reporting `error`. Correlate app and lightwalletd logs, including `background wallet synchronization failed`, with status observations. Owners: `synchronize_wallet_until`, `refresh_wallet_snapshot_until`, `scan_is_publishable`, and `reconcile.rs::{sync_wallet,find_rewind}`. `mining.rs::MiningCoordinator::run` can report all blocks generated yet fail synchronization; do not blindly mine again.

4. **Investigate the browser only after comparing its response with the server snapshot.** If raw accounts contain the expected change but the page does not, inspect requests, response/schema errors, query data, and `/api/v1/events`. [useServerEvents.ts](/private/tmp/zcash-skills-eval-20261016/stale-wallet-balance/without-skill/web/src/hooks/useServerEvents.ts) maps `wallet` to accounts/activity/quotes, `sync` to status, and `chain` to status/explorer queries. Snapshot publication emits `wallet` only when accounts change. Mining polling does not refresh accounts. `AppProviders` disables focus refetch; its five-second stale time is not polling. Test reload/refetch and disconnected-event recovery separately: the hook has no reconnect invalidation, and the server stream has no replay history.
